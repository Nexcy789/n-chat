01全景

一个 Node 进程里跑着插件，三个 agent 各自一个会话，外部能力都是独立进程。

三个角色 不是三个进程，是同一个进程里的三个 agent 会话。所谓「群聊」是 webchat 自己维护的一条 chat.jsonl 消息流 + 每个「角色×会话」一个游标，不是 DSH 原生的群概念。

02一条消息的旅程

从你按下发送，到她的话出现在屏幕上，中间有 9 个可以出错的点。

① 收下落 chat.jsonl，立刻给前端看
② 记账情绪：想念 −25%、恼火 −20 点
③ 合并窗口4.5 秒，连发的并成一批
④ 协调器决定谁接、谁先说
⑤ 拼料游标之后的 80 条 + 心情段 + 时钟
⑥ 投递agent.followup()
⑦ 收流assistant/message 事件累积
⑧ 合并收尾静默 1.5 秒 / 等工具 90 秒
⑨ 切段入库逐条 append，前端 1.6 秒内看到

这条链上的三个窗口

你说完等下文mergeWindowMs 4500
她说完等下文MERGE_IDLE_MS 1500
她在调工具90000
投出去等回音（兜底）REPLY_TIMEOUT_MS 360000

失败时的处理

  • 游标在投递之前推进；followup 抛错就退回去
  • 真超时（6 分钟）强制放锁，这一轮她看不到的内容不会补
  • 模型只调工具没正文：不落消息，只放锁
  • 第二个说话人失败：现在也会放锁（今天修的）

03协调器 · 谁接话

群是公开场合，三个人都回就是刷屏加三倍成本。这一层只回答一个问题：这条谁接。

私聊 优先级 1
不掷骰，只有一个候选，直接 reason: private
@所有人 优先级 2
三个都接，顺序 Fisher-Yates 打乱。每人最多 2 条（reason: all）
正则：@?所有人 | @全体 | 全部人都在 | 你们仨 | 你们三个
排在点名之前判 ——「大家都听听角色二怎么说」里也有「角色二」
点名 优先级 3
被点的先接，不受话痨值影响，也不受连说上限影响
点两个时，第二个 mentionedSecondChance 0.5 概率也接
判定是纯 text.includes(名字)，中文不做分词
掷骰 兜底
每人按话痨值独立掷一次：角色一 0.7 / 角色二 0.6 / 角色三 0.8
期望 2.1 人进池，2.4% 概率一个都没有 → 这条不回
连说上限（maxConsecutive 2）现在不生效，今天定下不做

掷中之后谁先说：加权抽签，不是取最高

W = 0.4 × 情绪分 + 0.6 × 沉默分 + 0.02

情绪分 = max(七维) / 100          ← 含恼火（今天补进去的）
沉默分 = 距上次开口 < 10 分钟 → 0
         10–60 分钟 → (分钟 − 10) / 50，线性到 1
         超过 60 分钟 → 1

2000 次模拟（今天改完后跑的）

场景角色一角色二角色三无人接
情绪都 30；角色一刚说完 5′，角色二 40′，角色三 80′15%27%56%3%
角色一情绪 90 但刚说完；另两个 3025%26%47%2%
三人情绪 60、都 20 分钟没说话34%25%39%2%
第二行是关键：情绪顶到 90 也救不回「刚说完」，沉默权重更高。这就是当初换掉「取最高分」的原因 —— 2026-11-26 角色一靠高分垄断了一整晚。
这里还缺一块：连说上限是唯一的「强制换人」机制，现在没生效。意味着一旦有人情绪高又话痨， 她能连着接三四轮，只靠沉默分慢慢压。你觉得掷骰已经够用，那就先这样。

04协调器 · 消息怎么推

同一份消息流，往三个方向分发：给模型、给网页、给手机。三条路的节奏完全不同。

给模型

按游标取 未读，上限 80 条，超了取最近的
拼三段：场景行 + 心情段 + 消息行
消息行带时间戳和 [语音] [发了一张图] 标记
投完立刻推游标（失败才回退）

给网页

每 1.6 秒问一次 /api/state?slim=1
只回版本号 rev + 锁 + 送达 + 情绪
版本变了才拉全量（四个会话各 200 条）
没变就只更新「正在输入」和「已发送」

给手机

前台服务开一条长轮询：
/api/poll-all?after=&wait=25
挂 25 秒，有新消息立刻返回
只推「别人发的」，自己发的不提醒
界面可见时不弹通知

投给模型时，她到底看到什么

【你现在的心情】想他·强（系统按情绪算的，说出口别复述这几个字）
→ 黏人、想贴着他，说话带点撒娇和「你都不理我」。

[群聊 · 现在是 19:30 · 你在群里，另外还有角色二、角色三。下面是你没看到的消息]
他（18:40）：晚上吃什么
角色一（18:42）：汤炖上了
他（19:28）：我先去洗澡
心情段只在「主导情绪 + 强度 + 语气」这个签名变化时注入一次，群聊和私聊各算各的。 每次都说会把她逼成复读机。

05情绪系统

七维是慢变量（小时级），管的是「她心里怎么样」；静默加成是快变量（分钟级），管的是「这个场合该不该有人说话」。

静默加成：impulse.mjs 并进来之后

原来 impulse.mjs 是另一套模型：给每人记「他多久没来」和「群里安静多久」两个 0–100 的数， 按分钟往上爬，过了 65 挑人开口，状态存在 impulse.json。 它和七维里的「想他」重复，所以现在只保留它唯一有价值的那条直觉： 

开口分 = 情绪分（七维最大值） + 静默加成

静默加成：安静 < 12 分钟   → 0（硬门槛本来就挡着）
         12 → 90 分钟       → 线性 0 → 30 分
         > 90 分钟          → 30 分封顶
群里安静12′30′60′90′+
加成0+7+18+30
这套数是照着「1.4–2 小时一条」定的。安静一个半小时加满 30 分，情绪只要攒到 25 就够 55 的门槛； 全局冷却 100 分钟兜住下限。实测（09:00 起沉默 15 小时）：8 次，间隔 100 分钟， 10:25 → 22:05 用完全天额度。凌晨 01:00–08:00 是静默段，不烧额度。

06和 DSH 的关系

插件跑在宿主进程里，借它的会话、模型、人格注入和事件流；能力靠全局钩子和外部进程。

依赖宿主的五件事

用什么干什么
ctx.get('agents')拿 agents 服务，建/取会话
agents.create()新会话必须是 session-<uuid>，且要显式带模型
agent.followup()投一条消息进去
ctx.on('session/event')听 assistant/message，按块类型判断正文/工具
agent.ctx.inject(['systemPrompt'])把 AGENTS.md 当人格注入，不是当工作区说明

三个全局钩子

钩子谁调干什么
__nchatSinkdsh-cover翻唱音频入流
__dshMediaEmitpainter画好的图入流
__dshVoiceSynthdsh-voice文字转语音
钩子没有版本协商，谁先注册谁生效。插件重载会清空。

最容易坏的地方（按概率排）

位置为什么脆坏了的表现
附件 image block宽高必须和文件真实尺寸一致，DSH 会校验整条消息被吞，不报错，永远等不到回复

全局钩子没有版本、没有超时翻唱/画图的产物插错会话或干脆不进流

07还要改什么

按「会不会咬人」排，不按工作量。

1. 模型不回话时，整群锁 6 分钟 建议改
REPLY_TIMEOUT_MS = 360000。今天 15:05 就撞到一次：投递后零事件，六分钟里你发什么都进不来。
改法：缩到 120–150 秒，或者收到第一个事件就重置一次计时。
2. 上传图只留 500 张，会删掉历史消息还在引用的图 建议改
pruneUploads() 按修改时间删，不看 chat.jsonl 有没有还在用。现在 36 张，一个多月后见。
3. 七个配置键不在白名单里 可改可不改
groupName / memeChance / memeGapMin / greetingChance / greetingEnabled / greetJitterSec / impulseJitterSec。
改了也不会立刻变行为（profile 里根本没写这些），只是把开关装上。修之前先确认 memeChance: 0 的零值判断。
4. 主动开口的机会几乎全给了角色一和角色二 建议改
pickByMood 取情绪分最高的那个。角色三的想念倍率 0.9（最慢），永远排第三。今天模拟 8 次，她 0 次。
改法：像协调器那样按权重抽签，或者给「上次开口的人」一票否决。改的是判定，不是参数。
5. 8 次额度和「1.4–2 小时」是打架的 取舍题
8 × 100 分钟 = 13 小时。醒 16 小时的话，最后 3 小时不会有主动消息。要铺满就得加额度，要更快就得压冷却，两个一起调会前密后空。
6. 连说上限：不做 既定
掷骰权重里已有「刚说完的人权重低」的抑制。代价是情绪高又话痨的人仍可能连说三四轮。
7. 还有一堆没接的库函数 清理项
policy.mjs 二十来个导出只用了 4 个；attachment.js 的写附件函数没人调； flushTurn 里有一段重复代码；前端 readAt 只存不用。
整体判断：主干是清楚的 —— 一条消息流、每人一个游标、协调器只做「谁接」、情绪只管「语气和时机」。 剩下的问题分两类：一类是收尾（超时兜底、图片清理、配置白名单），改起来都是几行； 另一类只有一个 ——「开口机会不均」，那要动 pickByMood 的判定逻辑，其余都不动架构。
